AI FACTORY — BUILD • BREAK • SURVIVE
Expo-Ready Product & Development Specification for Antigravity
**Project type:** Real-time 5-player cooperative mobile-controller game  
**Primary display:** One large host screen / TV / projector  
**Player devices:** 5 mobile phones, browser-based  
**Framework:** Air Jam  
**Frontend:** React + TypeScript + Vite  
**Styling:** Tailwind CSS  
**Game objective:** Five engineers operate different departments of one AI Factory and collectively deploy a healthy AI system before the timer ends.
---
1. Executive Summary
Build a polished, expo-ready multiplayer game called **AI Factory — Build • Break • Survive**.
The experience is designed for an office technology expo themed around:
**“AI is Engineering & Engineering is AI.”**
Five visitors join a shared game by scanning a QR code displayed on the host screen. Each visitor is assigned one engineering role. Every role receives a completely different mini-game on their own phone. The five mini-games run concurrently and contribute to a single shared factory state.
The big screen does not display the phone games. It displays a visually rich AI Factory with five departments, live progress meters, alerts, animations, the central AI Core, a countdown timer, Factory Health, and the final team result.
The game should feel like a **cooperative engineering mission**, not a quiz.
The five roles and mini-games are:
1. **Power Engineer → Tap-Tap Power**
2. **Data Engineer → Data Cleaning / Sorting**
3. **Security Engineer → Zip-Zap Firewall**
4. **AI Model Engineer → AI Core Puzzle**
5. **Cooling Engineer → Gyro Temperature Control**
At the end of the session, the five department results are combined into:
Department completion
Factory Health
Team Score
AI deployment status
If the factory reaches the required success conditions, the final screen announces:
**AI FACTORY ONLINE — AI SUCCESSFULLY DEPLOYED**
Otherwise:
**AI FACTORY FAILED — AI DEPLOYMENT UNSUCCESSFUL**

2. Product Principles
2.1 Five people, one system
Each player should feel responsible for one real part of the factory.
No player should feel like they are independently playing a generic arcade game.
2.2 Immediate cause and effect
When a player performs an action on their phone, the big screen must visibly react.
Examples:
Power tapping increases factory energy.
Data sorting increases data cleanliness.
Zip-Zap blocks an attack and strengthens the firewall.
Solving the AI puzzle improves the AI Core.
Tilting the phone stabilizes temperature.
2.3 Spectator readability
A person walking past the booth should understand the game in approximately 5–10 seconds:
“Five people are controlling five parts of an AI Factory. They have to keep it alive and deploy the AI.”
The big screen must therefore prioritize:
Factory visualization
Department status
Large progress meters
Alerts
Animated feedback
Countdown
Factory Health
Final success/failure
2.4 Low friction
Players should not install an app.
Expected flow:
Scan QR → open browser → enter/join → receive role → play
2.5 Short session
Target session length:
2–3 minutes
The game should be understandable immediately and replayable many times during an expo.

4. Air Jam's Role
Air Jam should be treated as the **multiplayer game infrastructure layer**, not as the game itself.
The project owns:
Mini-game logic
Factory simulation
Visual design
Scoring
Department progression
Game events
Success/failure rules
Animations
AI Factory theme
Air Jam provides the foundation for:
Host/controller architecture
Player rooms
QR joining
Phone controllers
Real-time input transport
Shared state synchronization
Host-authoritative actions
Controller/host separation
The implementation should use Air Jam's official SDK and current project scaffold rather than recreating WebSocket room infrastructure manually.
Air Jam currently documents a React/TypeScript model with host and controller surfaces, a typed input schema, and a shared store with the host as source of truth.
Official project bootstrap should be verified against the current Air Jam documentation before implementation because SDK APIs can change.

15. Factory Health
Factory Health is the combined health of the five departments.
Start with a simple transparent calculation.
Example:
Factory Health =
(
Power
  + Data
  + Security
  + Model
  + Cooling
) / 5
This is only the initial MVP formula.
The implementation should isolate the calculation in a single function so it can be tuned during playtesting.
For example:
calculateFactoryHealth(state)
This allows later experimentation with:
weighted departments
critical failures
interdependencies
event penalties
bonuses
completion thresholds
without rewriting the mini-games.

32. Security / Trust Model
Because this is a multiplayer game, do not trust controller-submitted scores.
Controllers should send:
“I performed action X.”
The host determines:
“Action X is valid and therefore gives Y points.”
Never allow the controller to directly submit:
score = 10000
power = 100
The host-authoritative model should remain the source of truth.

34. Antigravity Development Rules
The coding agent must follow these principles:
1. **Do not rebuild Air Jam networking from scratch.**
2. Inspect the installed/current Air Jam scaffold before changing architecture.
3. Follow the current Air Jam SDK conventions.
4. Keep host and controller responsibilities separate.
5. Keep the host authoritative for shared state.
6. Use typed contracts for controller input.
7. Keep game logic separate from UI.
8. Keep all gameplay constants configurable.
9. Build one working vertical slice before implementing all five games.
10. Never sacrifice reliability for visual effects.
11. Test every important interaction on a real mobile device.
12. Do not add external dependencies unless they solve a concrete requirement.
13. Do not introduce FastAPI, PostgreSQL, Redis, or an external AI service unless the implementation actually requires them.
14. Preserve a clean, modular architecture so individual mini-games can be modified independently.
15. Make the final UI polished enough for a public expo.

PROMPT START
You are the lead full-stack game engineer responsible for building an expo-ready real-time multiplayer web game called:
AI FACTORY — BUILD • BREAK • SURVIVE
The game is designed for a technology expo with the theme:
“AI is Engineering & Engineering is AI.”
The game must support exactly **five active players as a team**.
Each player uses their own phone browser. A computer/TV/projector acts as the host screen.
The five phones must display five DIFFERENT mini-games simultaneously.
The host screen must NOT display the five mini-games. It must display one shared visual AI Factory whose departments react to the players' actions.

   - lifecycle
   - deployment

GAME CONCEPT
Five engineers are responsible for keeping an AI Factory operational.
Roles:
1. Power Engineer
2. Data Engineer
3. Security Engineer
4. AI Model Engineer
5. Cooling Engineer
Each engineer has one different mini-game.
The five mini-games collectively determine the health of the AI Factory.
The experience should feel cooperative.
The players should need to communicate with each other.
The audience should be able to understand the factory state from the large screen.
---
FIVE MINI-GAMES
1. POWER ENGINEER
Mini-game:
TAP-TAP POWER
The player must repeatedly tap a large power button.
Every valid tap increases the power meter.
Target is configurable.
Example:
POWER 42%
[ ⚡ TAP ⚡ ]
Target: 100%
When power reaches the required target:
POWER ONLINE ✓
Host department becomes complete.
Use discrete/pulse-style controller input for taps so individual rapid taps are not lost.
---
2. DATA ENGINEER
Mini-game:
DATA CLEANING
Display a mixed set of data entities.
Example:
42, AI, 7, ML, 18, DL, 91, AI
The player must drag each entity into the correct group/category.
Correct sorting increases Data Cleanliness.
Incorrect sorting should not award progress and may apply a small penalty.
At 100%:
DATA PIPELINE CLEAN ✓
Host should show a visually clean data pipeline.
---
3. SECURITY ENGINEER
Mini-game:
ZIP-ZAP FIREWALL
The player must respond to a sequence of ZIP and ZAP actions.
Example:
ZIP → ZAP → ZIP → ZIP → ZAP
Provide large touch buttons.
Correct actions increase Firewall Strength.
Incorrect actions increase Threat Level or reduce security progress.
When complete:
FIREWALL ACTIVE ✓
The host should show a visible cyber-attack being blocked.
---
4. AI MODEL ENGINEER
Mini-game:
AI CORE PUZZLE
This must remain a small puzzle.
Do not turn it into a complicated game.
Example:
Arrange:
DATA
TRAIN
PREDICT
DEPLOY
Correct order:
DATA → TRAIN → PREDICT → DEPLOY
The puzzle should be quick, intuitive, and AI-themed.
When solved:
AI CORE OPTIMIZED ✓
Model/AI Core progress reaches its target.
---
5. COOLING ENGINEER
Mini-game:
GYRO TEMPERATURE CONTROL
Use the phone's device orientation/gyroscope where supported.
The phone tilt controls cooling/temperature.
Target safe range:
70–75°C
Example:
91°C → 84°C → 79°C → 75°C → 74°C
The player must stabilize the temperature in the safe range.
Implement mobile orientation permission handling.
If orientation data is unavailable, provide a touch-based fallback so the game remains playable.
When stable:
TEMPERATURE STABLE ✓
